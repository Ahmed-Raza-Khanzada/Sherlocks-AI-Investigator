Sherlock agent plan

Two teams share one case board. The Officer team talks to the user and makes sure every question gets a correct answer. The Sherlock team works quietly to solve the case. The Question desk sits between them, so a question is never asked twice and every answer the user gives reaches Sherlock.

How it works

Two flows through the Officer team

A · The user asks a question

  1. O4 Case briefer hands O1 the context pack: the whole chat, the case summary, Sherlock's latest view, and the facts that match this message.
  2. O1 reads the message with that context: language, who it is about, what exactly is asked.
  3. If the pack is not enough, O1 asks the toolbox: a report page, CDR query, or the API router.
  4. Still not in the facts, or the user asks for an opinion ("kya ye shamil hai?")? O1 asks Sherlock what he thinks.
  5. O1 drafts the answer as content, not final wording: the direct answer, facts with sources, evidence quotes, Sherlock's view labelled as his view.
  6. O2 checks the draft. If it fails, it goes back to O1 once with the reasons.
  7. O5 Presenter writes the checked answer for the user: in their language and a layout that is easy to read.
  8. Then O1 takes the top approved question from the Gatekeeper, if one is waiting, and asks it after the answer.

B · The user answers or gives information

  1. O1 sees an answer or new information, not a question.
  2. O3 records it on the case board in the user's own words, with the turn it came from.
  3. If it answers a question the user was asked, the Question ledger marks that question answered and stores the answer.
  4. The board change wakes the Sherlock team. Sherlock re-assesses with the new information.
  5. The Questioner proposes the next questions. The Gatekeeper filters them before the user ever sees one.
  6. O1 thanks the user briefly and says what it recorded, so the user knows it was understood.
  7. If the user changes something they said earlier, it is a correction, not new information: see Corrections.

The CDR team

A team of its own, because a CDR is not a document to read once. It is thousands of rows that need cleaning, lookups, pattern work and mapping, and it gets more valuable when a second CDR or the incident pin arrives. The team starts the moment a CDR is provided and writes every finding to the case board with the rows it rests on.

Asking Sherlock

  1. When. The toolbox found no fact, or the user asks for a judgment: why, how, is he involved, what next.
  2. Quick, not full. One model call, no tool rounds, with a 4-second budget. Sherlock answers only from his stored assessment and the context pack. He does not start a full background run while the user waits. Over budget: the reply says "Sherlock is looking into it" and his view comes later as a follow-up.
  3. Labelled. The reply keeps facts and opinion apart: "Records mein ye nahi hai. Sherlock ka andaza: …". The Answer checker enforces this.
  4. Remembered. The question and Sherlock's view go on the board. If the question needs real work, Sherlock picks it up in the next background run and the user is told when he has more.

Reply time budget

Everything runs on our own model server (Qwen 27B, configs/default.yaml). A chain of six model calls in a row would take too long, so each step has a time limit and a fallback, and most steps are code. Target: first words on screen within 3 s; the whole reply usually under 8 s, never over 20 s.

While the user waits: the live status line

The user should never stare at dots. While a reply is being worked out, the chat shows one short line saying what is running right now, in the user's language. A light band sweeps across the words from the first character to the last (right to left for Urdu). built in app.js, app.css, conversation.STATUS.

Reading your message

How it works

  1. Status events. Before each slow step, the turn sends {"type":"status","key","tool","text"} over the existing /graph/investigate SSE stream: reading, understanding, case board, counting, police systems, Sherlock thinking, each investigator tool, writing, checking.
  2. Fixed text, user's language. Lines come from STATUS and TOOL_STATUS in English, Roman Urdu and Urdu, never from the model, so they can't make things up. Names and systems are filled in: "Checking NADRA · Kamran Ahmed", "FIR file mangwa raha hoon".
  3. No flicker. Each line stays at least 450 ms; quick steps are skipped over. After 8 s the seconds appear ("9s"), so a slow lookup is visibly still working.
  4. Replaced by the answer. When the reply arrives, the line disappears. Later, the Presenter's streamed words take over from it.

Rules

  • One line at a time, the step running now. No step list or agent names.
  • Says what is being checked, never what was found. Findings belong in the checked answer.
  • Background work (Sherlock team, CDR team) shows its own small status on the case board, not in the chat.
  • Screen readers hear it through role="status". With reduced motion, the text stays still.
  • Urdu keeps its letters joined: the sweep is a gradient over the whole line, not separate letters.
  • As the plan's agents arrive (O4, O2, O5, Question desk, CDR team), each sends its own status lines.

The Answer checker

The one agent whose only job is that the user gets a correct answer to what they asked. Nothing reaches the user without passing it.

Answered what was askedThe first sentence answers the actual question. "How many FIRs?" must start with a number, not a summary of the case.
CorrectEvery number matches the computed count. Every name, date and FIR number exists on the board or in a tool result.
SourcedEvery claim cites a real F#, D# or call id. A claim with no source is removed.
ConsistentNothing contradicts what the user stated earlier or what the records say. A conflict is shown as a conflict, not hidden, and the order of trust (below) decides which source the answer leads with.
Honest about gapsIf the tools found nothing, the reply says so and names what was checked. No guessing.
LabelledSpeculation from Sherlock is marked as a suspicion. A question from the Questioner comes after the answer, never instead of it.

On failure: back to the Officer agent once, with the reasons. If the reason is missing data, the Officer agent may ask the toolbox one more time. If it still fails, the reply goes out with a visible warning on the part in doubt.

Which source wins

Tiers say how sure a claim is (fact, inference, speculation). Trust says who it comes from. When two sources disagree, the answer leads with the more trusted one, shows the other next to it, and names both. Nothing is deleted. Sherlock, the Answer checker and the Summarizer all use the same order, so they never pick different winners.

The Presenter

The Officer agent works out what to say. The Answer checker makes sure it is right. The Presenter decides how the user reads it: in their own language, laid out so the answer is clear at a glance.

Same language as the userUrdu script gets Urdu, written right to left. Roman Urdu gets Roman Urdu. English gets English. It follows the user's latest message, so switching language mid-chat works.
Answer firstThe first line answers the question in bold: a number, a name, yes or no. Detail follows only as much as the question needs.
Layout fits the contentThree or more items become bullets. FIRs, calls or people compared side by side become a small table. A short answer stays a sentence.
Evidence shown, not just citedKey points carry a short quote from the record with its source, e.g. FIR file page 2 or CDR rows 311–318. Quotes stay in the record's language, with a translation when the user's language differs.
Fact and opinion apartSherlock's view sits in its own labelled block ("Sherlock ka andaza"). Missing information is said plainly. The next question comes last, on its own line.
Nothing changes in transitNumbers, names, FIR numbers, CNICs, phone numbers and sources are copied exactly. A format guard compares them with the checked answer before sending.

Sherlock's Questioner proposes questions. The Gatekeeper decides which ones the user will see. The Question ledger remembers every question by its topic, so the same question in other words is still caught.

Builds on questioner.py, which already has topic keys, the ask count and the "closed when known" rule. The Gatekeeper moves those rules out of the Questioner into their own step, so every question passes the same check.

Corrections

"Nahi, 2 March tha." "Kamran nahi, Imran ne fire kiya." A correction is not new information. The old answer has to stop being used, and everything built on it has to be checked again.

What happens

  1. O1 spots it. Words like "nahi", "galat", "actually", "درست کریں", plus a value for a topic already on file. If O1 isn't sure, it asks once: "Pehle aap ne 1 March bataya tha. 2 March kar dun?"
  2. O3 replaces, never deletes. The new statement is written with replaces: S7. The old one is marked replaced and stays visible in the history.
  3. The ledger updates. The question's answer changes, and the record shows both turns.
  4. Everything built on it is flagged. Every board entry keeps the ids it rests on. Each entry built on the old statement, directly or through other entries, is marked stale and drops out of answers until it is redone.
  5. Redo. Each stale entry goes back to the agent that made it: R4 for location, R6 to re-file facts under a different person, A4 for dossiers, S1 for hypotheses. This is one event, not one per entry.
  6. Tell the user. "Note kar liya: waqia 2 March. Tower aur CDR ka jaiza dobara ho raha hai." If the user's earlier reply relied on the old value, the follow-up says what changed.

How the API router picks a system

  1. Topic. The ask is mapped to a topic: work, vehicle, phone, hotel, identity, property, complaint, record, FIR file, lab.
  2. Catalog. Each system lists the topics it answers, the identifier it needs, its output and its trust level. The model can only pick from this list.
  3. Identifier check. A CNIC-only system is called only when the person's CNIC is known. Otherwise the lookup that finds it runs first.
  4. Memory. Systems already searched for that person are skipped, including the ones that found nothing.
  5. Write back. Data becomes facts with a call id. Nothing found is recorded too. A topic no system holds gets "no connected system holds this".

The case report: Sherlock's full assessment

The PDF the officer downloads is Sherlock's work on the case, in full. Today case_report.assemble makes one model call over the graph and case file when the run ends, and keeps that PDF until rebuild=true. Nothing from the chat, the CDR team, Sherlock's hypotheses or the officer's corrections reaches it. In the new plan, S3 Report writer writes no new judgments. It lays out what the Sherlock team already concluded on the board, so the report and the chat always agree.

On download

  1. Up to date? The report is tied to a board version. If Sherlock's assessment already covers the current board, the PDF is built straight away (code only, about 2 s).
  2. If not, bring it up to date. If entries arrived after his last run, S2 → S1 → S4 run first. The officer sees "Sherlock is finishing his assessment…" with progress. Budget 90 s.
  3. Over budget. The report is built from the last assessment. The cover says "Assessment as of 14:02 (board v41). 6 newer entries are not yet assessed" and lists them in an appendix. The report never pretends to be newer than it is.
  4. S3 builds it. Report sections are filled from board entries; the model is only used to join them into readable paragraphs. Each paragraph keeps its ids.
  5. Checked like a chat answer. The O2 Answer checker runs on the report: every id exists, every number matches, speculation is labelled, no stale entry is used.
  6. Kept per version. The PDF is cached by board version, not once per run. A newer board means a new report, so rebuild=true is no longer needed.

Which agents use the AI model

An agent that follows fixed rules is written as code. Code is faster and cheaper, and it can't hallucinate. The model is used only where judgment or language is needed.

AI model

  • O1 Officer agent: understanding the question, drafting the answer
  • O5 Presenter: only for free-form answers; templates in all three languages handle the rest without the model
  • S1 Sherlock, S2 Summarizer
  • A2 Document reader, for scanned pages and photos
  • CDR R1 Intake, only for odd headers or a scanned CDR report
  • O2 Answer checker, only for "does this contradict something"
  • Q1 Gatekeeper, only to compare a free-form question with the chat

Code only

  • Q1 Gatekeeper topic-key checks, Q2 Question ledger
  • API router and its catalog
  • CDR team R2–R6: lookups, counts, distances, matching
  • O4 Case briefer, Board reader, Dossier, Chat memory (model only to summarise old chat turns)
  • O2 checks on numbers, sources and "was it answered"
  • O5 format guard: numbers, names and sources unchanged, language matches
  • O3 Statement recorder (model optional, for free-form statements)

Where the board lives

Today a finished run stays in memory for 30 minutes and is then served from graph_run (runs.py). The case file also travels inside graph["case"], which the host portal can save and post back. Once background agents write to the board between turns, that setup loses writes or lets an older copy win. The board moves to its own store.

Its own tableA case_board table keyed by run: one row per entry (fact, statement, question, assessment, dossier) and a version number for the board. Agents read and write the store, not the copy in memory, so eviction after 30 minutes loses nothing.
Add, never rewriteAgents only add entries. Changing an entry means adding a new one with replaces: F12. Two agents writing at once can't overwrite each other, and the history stays for the audit trail.
Every entry knows where it came fromEach entry stores by (which agent), event (which event or batch), from (the ids it rests on, used for corrections) and trust (its source rank).
Older saves are refusedgraph["case"] carries the board version. A portal save with an older version doesn't replace the board. Only the officer's own edits in it (roles, pin, notes) are merged in as new entries, and the reply returns the current board.
One snapshot per turnO4 reads the board at a single version. O1, O2 and O5 all work from that same snapshot, so a background write in the middle of a turn can't make the checker disagree with the draft.
Background runs survive restartsWaiting and running jobs are stored as job rows, the same way OSINT jobs already are (job_worker.py). After a restart, unfinished Sherlock and CDR runs start again from the last board version.

Safety and audit

The agents read untrusted text (OCR'd FIRs, uploaded files, OSINT and web results) and can call sensitive government systems. The rules below are part of the design, not a later add-on.

Document text is dataText from a document, upload, OCR or OSINT result is passed to the model as quoted content, never as instructions. It can never pick a tool, a person to look up, or a system. Only the officer's own message and Sherlock's assessment can lead to a lookup.
Lookups only for people on the caseThe API router only looks up people, numbers and CNICs already on the case graph or board, or named by the officer in this chat. A CNIC or number that turns up only inside a document needs the officer to confirm before it is looked up.
Officer's access appliesToday the portal token holds only the username (auth.py). Add the officer's allowed systems to the token. The API router checks them on every call, so the agents never get more access than the officer has.
Every call loggedWho (officer), which case, which agent, the reason (the turn or event), which system, which identifier, the result size and the time. Kept in the database and viewable by admins. A background call is logged under the officer whose case it is.
Limits per caseEach team has a limit on API calls per case and per hour. Going over stops the calls and tells the officer. A sudden jump in lookups is flagged to admins.
The checker checks quotes tooO2 drops any quoted text that isn't in the source document, using the existing quote_in check, so made-up or injected text can't appear as evidence.

Build order

  1. Live status line done. Status events before each step of a turn and each investigator tool; shimmer line in the chat. New agents add their own lines as they are built.
  2. Test set and timing. Fixed test chats in English, Urdu and Roman Urdu, including corrections and conflicts. Run them against today's agent to get a starting score and reply times. Log the time of each step on every turn.
  3. Board foundation. The case_board store with a version number; entries only added, with by, event, from, trust and replaces; tier, report type and page on every fact; refuse older portal saves. A change hook that wakes subscribers: debounced, batched, and never on an agent's own writes.
  4. Safety and audit. Document text as quoted data only; lookups limited to people on the case; the officer's allowed systems in the token; the call log; limits per case. In place before any background agent can call an API.
  5. Question desk. Move the dedupe rules into the Gatekeeper; ledger stores answers and the turn; rejected questions return with a reason.
  6. Answer checker. Add the answered-what-was-asked check, the honest-gaps check, the question-after-answer rule and the order of trust to the validator. Code checks first; the model only for claims no query computed.
  7. Corrections. Spot a correction, write the replacing statement, update the ledger, mark everything built on the old value as stale (via from), and send each stale entry back to the agent that made it as one event.
  8. Shared toolbox. Wrap board, dossier, chat memory, report reader, CDR and API router as tools both teams call, each team with its own budget.
  9. API catalog and router. Topics, identifiers, outputs and trust per system; remember searches that found nothing.
  10. Presenter. O1 hands a structured answer; O5 writes it in the user's language with the layout rules and the format guard. Templates first, streamed; if the guard fails, the template version is sent.
  11. Officer team split. O4 Case briefer builds the context pack (grown from case_memory); O1 gets it each turn, uses the toolbox, asks Sherlock for a quick view when the facts run out, and takes questions only from the Gatekeeper. Each step has its time budget and fallback; tool calls run in parallel; follow-up messages carry anything that finished late.
  12. Ingest. A1 Graph analyst streaming during the run; A4 Dossier cache.
  13. CDR team. Server path for known formats and a full own analysis for new formats or no report; compare the two when both exist. Split cdr.analyse into intake, enricher, patterns, location, cross-CDR and fact writer; add row references and re-runs on new pin, owner or CDR.
  14. Sherlock team in the background. S2 → S1 → S4 on events, writing summary, assessment and ranked gaps.
  15. Report writer from the board. Replace the one-shot _llm_written with S3 laying out the board: new sections for the assessment (H#), contradictions, suspicions, how the assessment changed, CDR analysis, statements and Q&A, chat views and "checked, nothing found". Bring the assessment up to date on download; store each PDF by board version; run the Answer checker on the report; template fallback. Tests for each step with real messages in English, Urdu and Roman Urdu.

Decisions needed

Sherlock's suspicions in chat?

Recommended: the Officer agent may mention them, clearly labelled as a suspicion. The alternative is to keep them in the report only.

Background budget

How many Sherlock runs and live API calls per case? Suggested: up to 20 runs and 30 background calls.

Sherlock on the dashboard

Show Sherlock's hypotheses live on the case board panel, or only when the user asks?

Report language

English only (recommended for court and file), or also in Urdu? Quotes stay in the language of the record either way.

Suspicions in the report

Recommended: include them in their own labelled section. Alternative: an "internal" version with suspicions and a "file" version without them.
