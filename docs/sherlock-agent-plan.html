Sherlock agent plan

Two teams share one case board. The Officer team talks to the user and makes sure every question gets a correct answer. The Sherlock team works quietly to solve the case. The Question desk sits between them, so a question is never asked twice and every answer the user gives reaches Sherlock. In v5 the Sherlock team gets specialists for claims, contradictions, statements and leads, a Skeptic that tries to break the leading hypothesis, and an Insight desk that brings what they find to the officer. v6 makes Sherlock settle which case is being investigated before it reasons about it, keeps a trace of every agent on every question, and gives the report one fixed reading order.

The agent trace

To see why a question got the answer it got, give the run id from the portal link (#run=…). The trace shows every agent that worked on each question and how they talked to each other.

  • steps: each node of the graph in the order it ran: the agent, how long it took, what it did and what it passed on

  • late: what finished after the reply had gone out

How it is built: three LangGraph graphs

Each team is one compiled LangGraph graph. The nodes are the agents. The edges are fixed in code or follow the model's own reading of the message, never words matched in it. The case board stays the only memory; a graph's state only carries the turn, the run or the report to its nodes.

Officer graph: one chat turn

  1. read O0 reads the message with the model: act, people, answer shape, depth, language. No model, or no answer from it: the turn goes to rules, the one node where the keyword rules live.
  2. record O3, when the officer tells us something: the model fills the recorder's fields, marks corrections and says which open question was answered. It also settles which case this is. v6
  3. brief A4 dossiers, O4 context pack, the Facts agent's exact counts, and every source the answer shape needs. Sherlock's quick view starts alongside when the reading says his judgment helps.
  4. draft O1 fills the shape's sections with source ids. If something is missing he names the lookups he needs: any toolbox tool, with its arguments.
  5. lookup The graph runs them in parallel. The live ones are the API agent. Then O1 drafts once more. Two drafts at most.
  6. desk Nothing found: said plainly, with every place checked. Then one extra item: a critical finding from the Insight desk, else the Gatekeeper's question.
  7. check O2, then present O5.
  8. trace Every node and model call of the turn is kept as one agent trace on the board. v6

Sherlock graph: one background run

  1. ingest A2 reads each record for its typed card and its recorded statements W#.
  2. entities A5, then register S10, then claims S5, then the presence matrix.
  3. contradictions S6, statements S7 and leads S8 work the same claims side by side.
  4. summary S2, then assess: S1's hypotheses and the hypothesis matrix.
  5. skeptic S9 challenges the leader; S1 answers each challenge once.
  6. questions S4, through the Gatekeeper, then insights Q3.

Report graph: one report

  1. freeze P1 fixes one board version.
  2. evidence P2, statements P3 and analysis P4 write their parts side by side.
  3. editor P1 writes part F and the annex and links the ids.
  4. persons P2 writes each person's own section, then relations P4 writes the ties pair by pair. v6
  5. summary P5, last. check P6 sends a failed summary back once.
  6. build P1 keeps the report with its board version. It runs after every Sherlock run.

What the Statement recorder writes v5

O3 used to keep the officer's words and the turn. That says what was typed, but not who the real source is, when the event happened or how sure the officer is. In v5 every statement is also broken into fields, so S5 and S6 can check it like any document.

The Insight desk v5

In v4, Sherlock's findings reached the officer only when the officer asked, or in the report. The team could find the key contradiction and nobody would hear about it. The Insight desk does for findings what the Gatekeeper does for questions: it decides what the officer is told, and makes sure nothing is told twice.

What can be passed on

  • A critical or major contradiction X#
  • A lead K# that changes a hypothesis, or one confirmed or ruled out
  • A hypothesis that changes status: supported, weakened, ruled out
  • A Skeptic challenge that S1 accepted against the leading hypothesis
  • A late result from a lookup or a background investigation the officer was waiting for

How it decides

  1. Rank. Critical first, then findings about the person or topic the officer is asking about, then newest.
  2. Told once. The ledger keeps every finding told, keyed by its id. The same finding in other words is not told again. A finding that changes (X3 resolved) can be told once more.
  3. One extra item per reply. A reply carries at most one finding or one question. A critical finding goes first; the question waits a turn.
  4. Checked. O2 checks the finding like any answer: ids exist, tiers labelled, speculation marked.
After the answerA finding never replaces the answer to what was asked. It comes after it, in its own labelled block: "Sherlock ki nayi baat (tasdeeq nahi)".
Critical can't waitIf a critical finding arrives while the officer is away, the case board panel shows it with a badge, and it leads the next reply.
The officer can pause it"Sherlock ki baatein baad mein" holds findings until the officer asks. The report holds all of them either way.

The case report: structured knowledge for the investigator v5

The PDF the officer downloads holds everything the teams know about the case, organized so an investigator can read it top down: first a structured summary in plain language, then the evidence, the statements, the analysis, one timeline and the actions to take. Its own Report team writes it and makes no new judgments. It lays out what is on the board, so the report and the chat always agree. Today case_report.assemble makes one model call over the graph and case file and nothing from the chat, the CDR team or Sherlock reaches it; v5 replaces that.

v6 The report is now read in a fixed order of eight sections, with the working material moved to the annex. This section describes the v5 parts those sections are built from: The report, in the order it is read.

The executive summary

One to two pages of plain-language paragraphs in a fixed order, covering facts, contradictions, leads, what is missing and what to do. Every sentence cites its ids, so a reader can jump to the detail. It is written last by P5 Summary writer, from the finished parts, and checked by P6 Report checker.

  1. The case in brief. FIR, offence, date, place, complainant, accused and their roles, in three or four sentences.
  2. What the evidence establishes. The key facts from records, reports and police systems (trust 1–2): FIRs, MLO, forensic, DNA, recoveries, Hotel Eye, tenant records, CDR.
  3. What is disputed. Every critical and major contradiction, both sides in one line each.
  4. Leads being pursued. The open and confirmed leads, each with its status and next step.
  5. Where the case stands. Internal version: each hypothesis with its status and Sherlock's labelled view. File version: the lines of inquiry, without ranking or views on persons.
  6. What is not clear yet. Each open point with the question that would clear it, plus pending reports and records not yet checked.
  7. Next steps. The top five actions, each with what it would settle.

How a report is built

  1. P1 freezes the board version and starts the parts.
  2. P2, P3 and P4 write their parts at the same time.
  3. P1 writes Part F and the annex and links the ids.
  4. P5 writes the executive summary from the finished parts.
  5. P6 checks everything. A failed section goes back to its writer once; if it fails again, it goes out with a visible warning.
  6. P1 builds the internal and file PDFs and caches them by board version.

Rules

  • The team never judges and never looks anything up. It writes only what is on the board.
  • All parts use the same frozen board version, so no part is newer than another.
  • The summary is written last, so it can't claim anything the body doesn't show.
  • Its writes never wake the Sherlock team, and the Sherlock team's run budget is not used.
  • If the model is down, every part is built from templates and the cover says so.

What makes it useful to an investigator

  • Linked ids. Every contradiction points to the evidence rows behind it; every evidence row lists the contradictions and leads it feeds. A reader can follow X1 to D10 and D14 and back.
  • Index by person. For each person, every page where they appear: role, records, statements, contradictions, leads.
  • Tables where things are compared. People, FIRs, records, contradictions and leads are tables; explanations are short paragraphs.
  • Tiers on every line. Fact, inference or speculation is marked, so nothing is read as stronger than it is.
  • Gaps are visible. Missing records and "checked, nothing found" are listed, so the reader knows what the report can't say.

On download

  1. Up to date? The report is tied to a board version. The Report team prebuilds it after every Sherlock run, so if the assessment covers the current board, the download is instant.
  2. If not, bring it up to date. The full Sherlock run goes first (S10 → S5 → S6, S7, S8 → S2 → S1 → S9 → S1 → S4), then the Report team. The officer sees "Sherlock is finishing his assessment…" with progress. Budget 90 s.
  3. Over budget. The report is built from the last assessment. The cover says "Assessment as of 14:02 (board v41). 6 newer entries are not yet assessed" and lists them. The report never pretends to be newer than it is.
  4. Checked like a chat answer. P6 runs on the report: every id exists, every number matches, speculation is labelled, no stale entry is used.
  5. Kept per version. The PDF is cached by board version. A newer board means a new report.

Where the board lives

Today a finished run stays in memory for 30 minutes and is then served from graph_run (runs.py). The case file also travels inside graph["case"], which the host portal can save and post back. Once background agents write to the board between turns, that setup loses writes or lets an older copy win. The board moves to its own store.

Its own tableA case_board table keyed by run: one row per entry (fact, statement, question, assessment, dossier) and a version number for the board. Agents read and write the store, not the copy in memory, so eviction after 30 minutes loses nothing.
Add, never rewriteAgents only add entries. Changing an entry means adding a new one with replaces: F12. Two agents writing at once can't overwrite each other, and the history stays for the audit trail.
Every entry knows where it came fromEach entry stores by (which agent), event (which event or batch), from (the ids it rests on, used for corrections) and trust (its source rank).
Older saves are refusedgraph["case"] carries the board version. A portal save with an older version doesn't replace the board. Only the officer's own edits in it (roles, pin, notes) are merged in as new entries, and the reply returns the current board.
One snapshot per turnO4 reads the board at a single version. O1, O2 and O5 all work from that same snapshot, so a background write in the middle of a turn can't make the checker disagree with the draft.
Background runs survive restartsWaiting and running jobs are stored as job rows, the same way OSINT jobs already are (job_worker.py). After a restart, unfinished Sherlock and CDR runs start again from the last board version.

Safety and audit

The agents read untrusted text (OCR'd FIRs, uploaded files, OSINT and web results) and can call sensitive government systems. The rules below are part of the design, not a later add-on.

Document text is dataText from a document, upload, OCR or OSINT result is passed to the model as quoted content, never as instructions. It can never pick a tool, a person to look up, or a system. Only the officer's own message and Sherlock's assessment can lead to a lookup.
Lookups only for people on the caseThe API router only looks up people, numbers and CNICs already on the case graph or board, or named by the officer in this chat. A CNIC or number that turns up only inside a document needs the officer to confirm before it is looked up.
Officer's access appliesToday the portal token holds only the username (auth.py). Add the officer's allowed systems to the token. The API router checks them on every call, so the agents never get more access than the officer has.
Every call loggedWho (officer), which case, which agent, the reason (the turn or event), which system, which identifier, the result size and the time. Kept in the database and viewable by admins. A background call is logged under the officer whose case it is.
Limits per caseEach team has a limit on API calls per case and per hour. Going over stops the calls and tells the officer. A sudden jump in lookups is flagged to admins.
No protected traitsSect, caste, ethnicity, religion and family name never count as evidence in any hypothesis, lead or answer. S9 and O2 both check for it. v5
The checker checks quotes tooO2 drops any quoted text that isn't in the source document, using the existing quote_in check, so made-up or injected text can't appear as evidence.

Testing Sherlock: golden cases v5

The 502 tests check that the parts work. They don't say whether Sherlock got better or worse at solving a case after a prompt or model change. Golden cases do.

What a golden case is

  • A closed case with a known outcome (anonymised), or a made-up case with planted contradictions, leads and a known answer.
  • Its documents, recorded statements, CDRs and a scripted officer chat in English, Urdu and Roman Urdu, including corrections.
  • An answer key: which contradictions exist, which lead mattered, which hypothesis is right, which people are the same.
  • Built with investigators. Start with 10, grow to 30. A few are held back and never used for tuning.
