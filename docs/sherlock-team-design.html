Sherlock: how the agent team works together

Fifteen agents around one shared case board. The officer talks only to the Conversation agent; it hands the message to the right specialists, and every reply is checked by the Validator before it goes out. Everything any agent learns goes onto the board, and the knowledge base makes all of it searchable for the next question.

The shared case board

Agents mostly do not message each other directly. Each one reads the board, does its job, and writes its result back with a source. Within one chat turn, the Conversation agent calls the others in order and passes their results along (see the graph below).

The team

Talks to the officer

Conversation agent

  • Detects the language (Urdu script, Roman Urdu, English) and replies in it.
  • Tells a question from a statement or an answer, even without a "?" ("kit ni fir in k uper ha").
  • Keeps the dialogue state: "ye", "us ke", "his" mean the person just discussed.
in: message · out: the reply
Understands

Understanding agent

  • Turns the message into a query: type and people.
  • Finds names written out, a distinctive word of a name, or by sound across scripts (altaf ↔ الطاف). Ranks such as "sub inspector" are not names.
in: message + focus · out: {type, people}
Knows everything

Knowledge base

  • Every person, record field, link, FIR file, case diary, lab and CRO report, upload and officer statement as a searchable entry.
  • Searches by words, topics in three languages ("kaam", "walid", "muddai") and sound.
  • A topic no record holds is reported as missing, not guessed.
in: question + people · out: cited entries
Computes

Facts agent

  • Exact answers by code: FIR count and list, FIR status (convicted, acquitted, under trial), serious FIRs, what each FIR alleges, criminals near a person or in the graph, connections, hotels, phones, vehicles.
  • Names crimes from the sections (324 attempted murder, 376 rape, 381-A vehicle theft, 384 bhatta…) and says his role in each FIR: an FIR where he is the complainant is never counted against him.
in: query · out: facts with sources
Reasons

Investigator (Sherlock)

  • Open questions that need reasoning or new data: plans tool calls, reads the results, writes tiered hypotheses (stated, corroborated, inferred).
  • Never expands the graph by itself.
in: question · out: conclusion, assessment
Goes and finds out

Research agent

  • When nothing gathered answers the question, it decides which APIs would, and calls them: FIR file, lab reports, CRO dossier, or the systems that hold a job, vehicle, phone, hotel stay or weapon.
  • Works without the AI model; the reply says what was checked live.
in: query + gap · out: documents, cited lines
Fetches

API agent

  • Calls the police systems, PSRMS FIR file, Labs, SAFE CRO, Hotel Eye and the CDR server's IMEI and nearest-police-station lookups.
  • Cache first; every call is budgeted and audited.
in: lookup request · out: records on the board
Reads

Document agent

  • Reads uploads (image, PDF, Word, Excel) and fetched documents; the vision model reads scans and photos in Urdu and English.
in: file · out: document D#
Telecom

CDR agent

  • Known formats go to the CDR server; new formats are mapped and analysed by the agent itself: top contacts, contacts on the graph, towers near the incident, IMEIs.
in: Excel + incident · out: CDR facts, phone-contact links
While the graph builds

Collector, Reader, Linker

  • Fetch every FIR file, lab report and CRO dossier found; read them into quoted facts; link the people named to the graph.
in: new FIRs on the graph · out: documents, facts, links
Records

Fact collector

  • Records what the officer states with their words: incident, roles, events. Matches an answer to the open question it fits.
in: officer's words · out: facts F#, incident, roles
Tells

Briefing agent

  • What is new since the last message. One short line unless asked or about the person discussed.
in: case board · out: news lines
Asks

Questioner

  • Finds gaps: where (map pin), what, when, main suspect, FIR, whose CDR, victim, vehicle, other suspects.
  • At most three open; asked at most twice; an answered question never returns.
in: case board · out: one question with a button
Checks

Validator

  • Every number must match the Facts agent; sources must be real; no contradiction with the officer's statements.
in: draft + facts · out: pass or fix
Writes

Report writer

  • The cited case report PDF when the graph finishes or is stopped: incident, targets, linkages, findings, documents, CDR results.
in: case board · out: PDF

The agents' steps are kept for the audit trail but not shown in the chat. The officer sees one natural reply, plus a warning only if the Validator still has a doubt. With the AI model connected, the model writes the reply from the same entries and facts; without it, the reply is a cited list.

A file is uploaded

  1. Check. Only image (JPG, PNG), PDF, Word (.docx) and Excel (.xlsx), within the size limit; anything else is refused with the reason.
  2. Document agent reads it. Photo or scan: the vision model transcribes it. PDF: text layer, scans by the vision model. Word: text and pictures.
  3. Call or tower data goes to the CDR agent. Known format: the CDR server's analysis. Unknown format or server down: the agent's own analysis.
  4. Linking. Numbers, CNICs and IMEIs in the file are matched to people on the graph; contacts become "in phone contact" links.
  5. Questioner asks what is missing. "Whose CDR is this?" · "Where did the incident happen? 📍 Pin on map"
  6. Knowledge base rebuilds, so the next question can use the file.

The incident is pinned on the map

  1. The officer presses 📍 Pin on map and clicks the spot, or types the coordinates.
  2. The pin goes on the case board; the "where" and "pin it" questions close.
  3. The API agent finds the nearest police station; the CDR agent checks which numbers used towers near the pin.
  4. The case report gets the incident point and these findings.

Guardrails

Sourced or droppedEvery fact quotes a system, a document or the officer's own words. A reply citing nothing real does not pass the Validator.
Numbers by codeCounts and statuses come from the Facts agent, never from the model's wording.
About that person onlyA question about Danish gets entries about Danish; nothing about someone else is offered instead.
Missing is saidIf no record holds the answer ("danish ka kaam?"), the reply says so instead of guessing.
BudgetsLive calls per question (6), documents per run (40), vision pages per file. Every call is in the audit log.
No silent graph changesAgents may suggest whom to search; only the officer starts a new search.
One fix, then a warningThe Validator returns a draft once; a remaining doubt is shown instead of looping.
Works without the modelRules carry understanding, facts, search and questions; replies become plainer, not wrong.
